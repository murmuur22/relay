# Embedded independent updater (0.6.4 source)

The desktop Updater remains a reserved, administrator-only trusted system app, not an editable registry app or a gateway proxy. Its read bridge browses broker snapshots without rotating the independent cookie. Start update now launches the independent application inside the existing Relay page. It does not open a popup or begin installation. Review, current-password authorization, install/cancel/rollback, real byte progress and recovery all use the independent application's existing HTTP and broker interfaces.

## Lifecycle and authority

`App.svelte` owns a separate maintenance surface outside the ready/login/window conditional. Clearing ordinary desktop windows on authentication loss does not remove its iframe. The independent HTML, JS, styles and API are served directly by updater-web, not by the runtime being replaced. A stopped Relay cannot strand already loaded monitoring code behind a runtime asset proxy.

The launch target still requires the canonical configured trusted HTTP hostname, a different port, `/updater/`, no query and a bounded one-use ticket fragment. The host navigates an initially blank iframe through `location.replace`; it never retains the ticket in a `src` attribute or storage. The child removes the fragment before its first request. Only the validated non-secret reviewed version may enter child history state. No password, cookie, CSRF, ticket or broker authorization is sent by postMessage.

The child can request sign-in using a one-field event. Both host and child validate the exact configured origin, exact window source and bounded message shape. The existing Relay Login remains in the same page, with an explicit Retry Relay connection when the service is stopped. The iframe stays mounted but hidden while Login is visible. Signing in again as the same active administrator restores visibility, closes old consent and reads current state; it never retries a mutation. A different account, explicit desktop logout, or observed live session replacement retires the surface. Closing the maintenance chrome only hides monitoring; Return to maintenance monitor restores it. End monitoring session in the independent application actually clears its HTTP session.

Updater-web requires the genuine Relay cookie at ticket exchange, validates the original active administrator, and binds monitoring to that cookie's digest and the runtime's random nonsecret `X-Relay-Runtime-Instance` observation. Every monitoring read checks the fixed Relay session endpoint. The identical admitted cookie retains read-only access during downtime/maintenance or a positively observed new runtime; a live 401 from the admitting runtime is revocation/expiry, not a restart. Missing or invalid runtime evidence does not qualify a restart. A removed cookie ends monitoring; a changed cookie must authenticate as the original active administrator. Successful reauthentication updates both bindings. The host applies the same restart-versus-live-revocation distinction and invalidates its launch epoch synchronously at logout intent. All mutations additionally require that exact user ID, a live administrator session, fresh password consent, updater-cookie CSRF and the broker's one-use target-bound authorization. Neither an old cookie nor a runtime identifier authorizes a mutation.

A cookie that changes while Relay is unreachable cannot qualify a new account and is denied. Already rendered content in a retained browser page cannot be recalled instantly: connected monitoring notices logout/account changes on its next bounded poll. Explicit host logout conceals and makes the surface inert synchronously. It retains the hidden recipient long enough to receive readiness, perform independent logout and confirm unauthenticated auth readback before acknowledging teardown. The host removes the frame on the exact-source/origin acknowledgement. A ten-second failure bound removes it with an explicit unconfirmed-termination warning, not a success claim; a new embedded launch cannot overlap an ending frame. This is a trusted first-party control plane, not an untrusted app sandbox.

## Framing policy

Only independently served HTML documents remove X-Frame-Options DENY. Their CSP permits `frame-ancestors` equal to the exact configured `relayOrigin`, including scheme and port, not a wildcard, hostname suffix, sibling port, or arbitrary site. Every ancestor must satisfy that policy; a hostile outer frame is blocked. API and asset responses keep their previous deny policy. Host, exact API Origin, CSRF, password, signed ticket, cookie, Unix-socket and privileged broker boundaries remain intact. No gateway/native cross-origin policy was relaxed. Standalone direct navigation remains allowed by CSP and uses the same independent authentication flow.

The public HTTPS Gateway edge is not a permitted substitute for the private HTTP management origin. Preserve the original private management/updater route and both forwarded ports. This redesign does not add TLS, DNS, trust-store, router, firewall or production configuration.

## Character rendering

Both independently built bundles use the pinned existing Three.js dependency. An opaque lit TorusKnotGeometry, core sphere/halos, orbit points and sparse curved particle points are depth-tested in a low-resolution WebGL target. One coherent luminance sample per stable cell is mapped to `. : + * # / @` on the visible character canvas. This is actual animated 3D shading/occlusion, not a wireframe, static image or recording. Rotation/precession and breathing use elapsed time. Real broker phases select scan/settle/pulse decoration; received artifact bytes alone supply numeric progress.

Rendering is bounded to at most 180 by 120 cells and an adaptive 15–30 fps ceiling. No device-pixel-ratio multiplication inflates the WebGL target. Hidden pages, offscreen surfaces and trusted host hiding pause animation; reduced motion/account preferences retain a calm static rendering of the real knot. Missing or lost WebGL gives an explicit text fallback, with status and controls still usable. Container queries stack the action rail by actual application width. All first-party accents, checkboxes and focus treatments remain warm neutral/cream.

## Distribution and migration gate

A runtime release does NOT replace `/opt/relay-updater`, its independent web server, UI, broker, configuration or units. Previously installed control planes still return DENY/frame-ancestors none and have their previous UI; a runtime-only update cannot enable this embedded design. The new runtime host and new independent web/UI must be distributed together for this feature. The broker protocol remains unchanged.

Fresh installations can package the changed independent control-plane archive through the existing separately attested two-artifact release process. Existing installations require a separately reviewed operator-controlled control-plane upgrade: verify genuine signed artifact provenance and exact hashes, back up the protected old control-plane/configuration/unit tree, coordinate the independent web/UI replacement and restart, then requalify exact configured ancestors, standalone access, real authentication, install/recovery and matching-state rollback. Do not reuse the fresh installer against an existing installation; it deliberately refuses adoption. No automated installed-control-plane migration, privileged self-update, signed new release, Linux/systemd qualification or production change is implemented or claimed here. Operators must retain the current standalone maintenance route until that migration is qualified. The host's explicitly requested Standalone recovery (new tab) button calls the original synchronous opener-severed launcher with a fresh signed ticket; it is never invoked by normal Start update or reconnect. It remains an administrator-authenticated manual recovery path, including when an old control plane refuses embedding. Its exchange rotates the shared updater cookie, so do not treat two simultaneously open consoles as independent mutation sessions.

Refreshing the entire Relay page while its runtime is stopped still depends on obtaining the Relay shell again. The guarantee is survival of an already mounted console through runtime auth loss/restart, not offline reload of the whole desktop or crash-proof browser recovery.
