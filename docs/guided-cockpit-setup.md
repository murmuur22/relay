# Guided Cockpit setup (local candidate)

Use Add app → Gateway → Next → Create new target → Set up Cockpit, or Control Panel → Gateway → Set up Cockpit. The existing Gateway listener must already be managed and enabled. If it is off, follow Set up Gateway first; the existing listener workflow provisions no DNS, Caddy, firewall or OS trust. Operator-owned and programmatic configuration remains read-only.

The seven steps are Destination, Certificate, Login, Live channels, Display, Permissions and Review. Typed fields produce the existing runtime target format; no JSON editing is needed. Cockpit profile v1 is declarative: entry `/`, private cookie `cockpit`, WebSocket `/cockpit/socket`, protocol `cockpit1`, server-derived upstream Origin, protected tab, admin-only. Other services are not qualified by this profile.

Use a canonical fixed private IPv4 origin, no credentials/path/trailing slash. Loopback is supported for disposable tests. HTTP has no upstream TLS; the operator must independently establish its network boundary. Continuing from Destination after changing HTTPS to HTTP removes the certificate DNS identity, custom CA path and TLS trust selection with a visible warning. Returning to HTTPS requires re-entering those settings; edits/navigation clear prior check results, password and acknowledgement and do not send traffic. HTTPS uses system trust or an operator-provisioned protected CA path and an optional exact DNS certificate identity (blank checks the IP). Files remain on the Relay server; no secret uploads or observed-certificate auto-trust. TLS identity/SNI does not rewrite HTTP Host. Browser-facing Relay HTTPS trust is separate.

Check destination now requires the current Relay password, exact Origin/CSRF and a live administrator. It validates the whole runtime reference and makes one credential-free, three-second HEAD with no redirects, body capture or credential-bearing diagnostics. Admission is one management operation at a time and five explicit checks per minute globally. Logout, expiry, revocation, demotion, client cancellation and shutdown invalidate checks through existing live-session operations. A configuration identity, source and time accompany independent tiers. HTTP 200, cookies or a socket never prove login, authenticated live interaction or termination. Those stages stay not-tested until separately qualified against authentic Cockpit. A manual acknowledgement is not a verified check.

Save target separately requires a current password and acknowledgement that applying configuration retires Gateway windows. Target configuration and app registration are not atomic. The original listener and unrelated targets are preserved; a base-config comparison refuses a stale save. A successful target save returns the app draft and selected target; finish the ordinary wizard and Save app. Cancelling app creation leaves a separately saved target. If the target-save response or readback fails, the UI blocks blind retry and asks for status reconciliation. In direct Control Panel setup, Return without creating another target reads authenticated Gateway state again. A failed refresh explicitly marks the state stale/uncertain and keeps changes disabled until a successful refresh; it does not confirm a save. In nested Add app setup, Cancel target refreshes Gateway options while retaining the app draft. Choose an already saved target rather than creating a duplicate.

Control Panel Gateway app registration supplies an exact-session, in-memory retry identity. An unchanged retry returns the same registered app; a changed request or changed/deleted app conflicts. This is not durable cross-restart or cross-login idempotency. After reload/sign-out or an uncertain outcome, inspect Apps before creating again. Existing generic, advanced, grants and first-run onboarding flows remain distinct. The Cockpit admin-only engine restriction wins over ordinary grants; upstream account privileges still apply.

Apply-password confirmation is not launch-time fresh authentication or configurable idle enforcement. Those are a separate before-production milestone. No toggles promise controls the engine does not enforce.

Qualification is separated: local synthetic Mac HTTP/TLS/compiled Chromium fixtures, parent authentic disposable Cockpit qualification, independent exact-source review, owner preview and any release/deployment. Chromium's exact fixture-SPKI exception is not upstream TLS verification, system trust or Safari qualification. Root stays 0.6.11, dependencies unchanged (the inherited install reported two low audit findings).
